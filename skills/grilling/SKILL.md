# 追问式设计审查（Grilling）

## 概述

在动手之前，用无情的追问把计划、决策或想法压瓷实。核心原则：**让每一个决策都显式化，而不是默认成立。**

本技能把讨论映射成一棵**决策树**：每个决定会挂上一组依赖它的子决定。我们按**轮次**推进，每次只问当前“边界”上的问题——即前置已经确定、现在就能回答的问题。你的回答会推开边界，解锁下一轮问题，直到整棵树被遍历完。

> 本技能不会替你执行任何操作，只负责逼你把事情想透。

## 何时使用

- 你刚拍板一个方案，想确认没漏掉关键风险
- 你要做一个影响较大的技术决策
- 用户说“帮我看看这个计划靠不靠谱”或任何含“拷打 / 追问 / 压力测试”意图的话
- 用户在 brainstorming 之后、writing-plans 之前，希望进一步收敛假设

## 如何使用

### 1. 建立设计树

把用户给的想法/计划/决策作为根节点，识别出它依赖的一级决策：

- 目标是什么？如何衡量成功？
- 范围包括什么、明确排除什么？
- 关键依赖有哪些？（人、系统、数据、权限、时间）
- 最坏情况是什么？失败模式有哪些？
- 有没有被默认成立的假设？

### 2. 按轮次追问边界

**边界（frontier）** = 前置已确定、现在就能问的问题。  
每一轮：

1. 列出当前所有边界问题
2. 每个问题编号，给出问题标题、正文和你的推荐答案
3. 等待用户回答，不要自己替用户决定
4. 用户回答后，更新设计树，计算新的边界，进入下一轮

问题格式：

```
❓ **Q1 - <问题标题>**：<问题正文，可含多个选项>

➡️ <你的推荐答案>

---

❓ **Q2 - <问题标题>**：<问题正文>

➡️ <你的推荐答案>
```

### 3. 事实 vs 决策

- **事实查找是你的工作**：如果某个边界问题需要环境信息（文件系统、工具输出、API 状态等），直接派遣子 agent 或调用工具去查，**不要问用户“你能帮我查一下吗”**。
- **决策是用户的工作**：涉及选择、优先级、价值观的问题，必须交给用户回答。

如果某个事实查找会阻塞后续问题，把依赖它的问题移到下一轮；不阻塞的问题本轮照常问。

### 4. 结束条件

当边界为空：设计树的所有分支都被访问过，没有未言明的假设时，本技能结束。

结束前向用户确认：

> “我们现在对 X 达成了共识。还有没有我漏问的假设？”

只有用户确认后，才认为达成了共同理解。**不要在此技能内直接执行计划。**

## 常见错误

- **自动替用户做决定**：推荐答案只是推荐，必须等用户确认。
- **一轮只问一个问题**：边界上的独立问题应该一次抛出，减少来回次数。
- **把依赖性问题放在当前轮次**：如果 Q2 的答案依赖 Q1，Q2 必须放到下一轮。
- **用提问掩盖事实查找**：能查的资料自己查，不要转嫁给用户。
- **未确认就结束**：边界为空只是结构上的结束，还要用户口头确认没有遗漏。

## 示例

用户：“我想给系统加一个实时通知功能。”

第一轮边界问题：

```
❓ **Q1 - 通知渠道**：用 WebSocket、SSE 还是轮询？各自的可靠性和运维成本差异很大。

➡️ 推荐 SSE，实现简单、兼容现有 HTTP 基础设施，除非需要双向通信再考虑 WebSocket。

---

❓ **Q2 - 失败模式**：如果通知服务宕机，是丢消息、延迟投递还是降级为静默？

➡️ 推荐明确选择降级策略，并定义可观测指标。

---

❓ **Q3 - 范围边界**：是所有事件都发通知，还是只针对特定类型？是否需要用户可配置？

➡️ 推荐先限流 3 类核心事件，后续通过配置扩展。
```

用户回答后，再基于答案展开下一轮（如“Q2 选择降级后，降级阈值是多少？通知谁？”）。

## 红线

- 不要在用户确认理解之前开始写代码或改文件。
- 不要在本技能内调用 writing-plans、brainstorming 或其他实现技能。
- 不要把推荐答案当成已确认答案推进。
